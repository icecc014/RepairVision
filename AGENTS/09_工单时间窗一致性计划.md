# 09_工单时间窗一致性计划（2026-09-10 拟定，次日执行）

## 1. 本次已完成的准备（2026-09-10）

- **布局设计器画布放大**（`frontend/pc-admin/src/components/LayoutDesigner.vue`）：
  - 对话框宽度 `980px → 1240px`，顶部间距 `5vh → 3vh`；
  - 网格最大高度 `52vh → 72vh`，单元格最小高度 `34px → 46px`，格间距 `3px → 4px`，内边距 `10px → 12px`；
  - 目的：默认 6×10 的画布在 1080P 屏幕上可完整显示且单格更大，方便拖拽绘制。

## 2. 待办需求（用户 2026-09-10 提出）

> 在工人维修页面与管理员页面中，主页的维修工单筛选应当与建筑的报修信息一致。
> 例如 3 天内只有 2 张维修单、7 天内有 8 张，当用户在主页选择"看 3 天内"时，
> 2D / 3D 视图里也只应显示这 3 天内的报修信息（红点数量、故障卡内容同步）。

## 3. 现状分析（已核查的代码事实）

| 位置 | 现状 | 问题 |
| --- | --- | --- |
| PC 工单总览 `views/HomeView.vue` | 有 1/3/7/30 天胶囊，默认 3 天，调用 `apiAdminOrders(..., days)` | 正确 |
| PC 建筑可视化 `views/BuildingVisualView.vue` | `apiAdminOrders(0, 0, 1, 200)`，**days 未传（=0 不限时间）** | 2D/3D 显示的是全部工单，与主页时间窗不一致 |
| PC 可视化组件 `components/AdminBuildingVisual.vue` | 只接收 `orders` 属性并渲染红点/故障卡 | 本身无过滤逻辑，取决于传入数据 |
| H5 工人端 `views/MapView.vue` → `/api/worker/map-data` | 后端 `logic/workermapdatalogic.go` 用 `ListOrdersByBuildingIDs(..., activeOnly=true)`，**无时间窗** | 工人端 2D/3D 永远显示全部未完成工单，与"我的工单"时间筛选不一致 |
| H5 宿管/工人工单列表 | 已有 1/3/7/30 天胶囊（V4-S1 已完成） | 正确 |

结论：**列表侧已经有时间窗，可视化侧没有**。需要把同一个 `days` 参数贯通到 2D/3D 数据源。

## 4. 方案设计

统一口径：时间窗一律按 `orders.created_at >= 今天 - (days-1) 天` 计算，与现有 `store.sinceForDays(days)` 完全一致；
红点规则保持现状（仅"待派单 / 已派单 / 维修中"显示红点，已完成与已取消不显示）。

### 4.1 后端（order 服务）

1. `order.api` + `internal/types`：`WorkerMapDataHandler` 增加可选查询参数 `days`（1/3/7/30，默认 3）。
2. `internal/store/order.go`：增加 `ListOrdersByBuildingIDsWithinDays(ctx, conn, buildingIDs, activeOnly bool, days int64)`，
   SQL 在现有基础上追加 `and created_at >= ?`。
3. `internal/logic/workermapdatalogic.go`：读取 `req.Days`，默认 3，传给上面的查询。
4. 可选：`/api/admin/orders` 已支持 `days`，无需改动。

### 4.2 PC 管理端

1. `views/BuildingVisualView.vue`：顶部新增时间胶囊（1 天 / 3 天 / 7 天 / 1 个月，默认 3 天），
   变更时以 `apiAdminOrders(0, 0, 1, 200, days)` 重新拉取并传给 `AdminBuildingVisual`。
2. 卡片上的"N 单"角标同步使用同一份过滤后数据（避免角标与红点数量不一致）。
3. `AdminBuildingVisual.vue` 无需改动（只吃传入的 orders）。

### 4.3 H5 工人端

1. `views/MapView.vue`：新增同样的时间胶囊，`apiWorkerMapData(days)` 重新拉取；
   `BuildingFloorPlan.vue` / `Building3D.vue` 共用同一份 `map.orders`，红点与故障卡自动同步。
2. `api/index.ts`：`apiWorkerMapData(days = 3)`。
3. 工人端"我的工单"页面已选的时间窗可记忆（localStorage），地图页默认沿用同一值，减少来回切换。

### 4.4 文案与提示

- 可视化页头部标注当前时间窗，例如"统计范围：近 3 天（2 单）"，让用户明确红点为何变少。

## 5. 次日执行顺序（建议）

1. 后端：`order.api` / `types` / `store` / `workermapdatalogic.go` 加 `days`，`go build ./...` 通过。
2. PC：`BuildingVisualView.vue` 加时间胶囊并透传 `days`，本地 `npm run build` 通过。
3. H5：`apiWorkerMapData(days)` + `MapView.vue` 时间胶囊，`npm run build` 通过。
4. 部署：`docker compose up -d --build order-api web`。
5. 回归验证（见第 6 节），随后补文档、提交、打标签 `v4.5`。

## 6. 验收标准

1. 造数据：让某楼栋 3 天内 2 单、4-7 天内再 6 单（共 8 单）。
2. PC：主页选 3 天 → 建筑可视化弹窗红点数 = 2；切到 7 天 → 红点数 = 8；切回 3 天 → 2。
3. H5 工人端：选 3 天 → 2D 平面与 3D 楼层红点数 = 2；切 7 天 → 8；与"我的工单"列表条数一致。
4. 已完成 / 已取消工单在任何时间窗内都不显示红点。
5. 切换时间窗不出现白屏、报错或红点残留（需要清空上一次的 orders 再渲染）。

## 7. 风险与注意点

- `days` 必须以"天"为单位、包含当天（`sinceForDays` 已用 `-days+1`），不要改成 24 小时制，否则与列表对不上。
- H5 地图数据是一次性拉取 buildings + orders，切换时间窗要重新请求，注意加载态与并发去抖。
- 建筑可视化弹窗打开时会二次拉取订单（`open()` 里），改造后要把 `days` 一起带上，避免先显示旧窗数据再刷新。
- 后端 `WorkerMapData` 新增参数不影响老客户端（缺省即 3 天），但要注意与"工人只看自己的楼栋"权限过滤叠加。
