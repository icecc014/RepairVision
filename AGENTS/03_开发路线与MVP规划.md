# 03_开发路线与MVP规划.md（阶段计划·随进度滚动更新）

> 01/02 描述的是终版目标形态；本文件描述“从空仓库逐步走到终版”的顺序、裁剪与验收标准。
> 本文档随开发滚动更新；阶段切换或范围变更后必须回写本文件并提交。

## 1. 开发总原则

1. 先跑通，后加肉：每个阶段结束都必须可演示、可提交、可回退，不允许留下“半成品堆到最后”。
2. 架构边界从第一天固定：3 个服务 / 3 个独立库 / 两套前端；后续阶段只加功能，不改边界。
3. 禁止为了 MVP 抄近路跨库直连；宁可先用种子数据 + 基础 RPC 把链路打通，后续再补实现。
4. 每个阶段只做本阶段清单内的功能；若发现清单与 01 的 F 编号冲突，先回写 01 再继续，禁止私自新增功能。
5. 工单状态写操作只允许发生在 order-api（本规则建议补入 AGENTS.md/01 红线，待人工确认）。

## 3. 已确认的设计决策（2026-09-07）

- A. MySQL 拓扑：采用“1个实例3个schema”（8容器）。
- B. 工单状态机：扩展 F14 为“开工+完工”（2→3→4），不新增编号。
- C. PC 管理端加入只读“工单总览”页，归属 F07 管理支撑，不单独编号。
- D. Kafka 仅在 P4 用于 F05/F19，不进 MVP 主链路。

### 已确认的设计决策（2026-09-08，P1开工）

- E. 种子数据由“数据属主服务启动时幂等补种”：worker-rpc 补用户+楼栋管辖、map-rpc 补楼栋、order-api 补维修类型；不依赖 MySQL 首次初始化，避免重置已有数据卷。
- F. P1 简单自动派单在工单创建事务内立即执行：订单 1→2 并绑定 worker、写 dispatch_records；取消入口保留到工人开工前（status 1/2），开工后不可取消。
- G. 三服务统一使用 root + `MYSQL_ROOT_PASSWORD` 连接单 MySQL 实例（DSN 指向 mysql:3306），各自只访问自己 schema。
- H. P1 起各服务主程序使用 `conf.UseEnv()` 展开 yaml 中的 `${VAR}`，密码与 JWT 密钥不落盘明文。

## 5. 里程碑说明

### P0：工程骨架跑通（无业务功能）

目标：仓库结构、镜像依赖、三服务调用链、双前端均可一键起。

- 建立目录：`services/order`、`services/worker`、`services/map`、`frontend/pc-admin`、`frontend/mobile-web`、`deploy/`、`db/init/`、`scripts/`
- goctl 生成 order-api(HTTP:8888)、worker-rpc(gRPC:9001)、map-rpc(gRPC:9002)，三服务均注册 Etcd
- 最小 gRPC health/ping 接口：order-api → worker-rpc / map-rpc 调用链打通
- 一个 MySQL 实例初始化 3 个 schema 及全部 DDL（含 02 中新增表），Redis/Etcd/Kafka 启动就绪
- 两套 Vite 前端脚手架可构建，Nginx 托管 `/admin/`、`/m/` 并反向代理 `/api`、`/ws`
- 提供 `scripts/` 一键启动/停止/日志命令

验收：`docker compose up -d` 后无手工步骤；三个服务 health 通过；两个前端页面可访问。

### P1：MVP最小业务闭环

目标：完成“宿管报修 → 自动派单 → 工人查看 → 单点完工”的端到端闭环，页面刷新即可，暂不做实时推送与可视化。

- 种子账号：admin、若干宿管、工人；工人绑定楼栋群，宿管绑定单栋
- JWT 登录 + 角色中间件；order-api 为唯一 HTTP 入口
- F07 宿管查看本栋工单、F08 创建工单、F09 未接单取消（取消即可）
- PC 管理端只读工单总览（管理员视角，不单独编号）
- 工人查看“我的工单”（F13 的基础列表形态）、F14 开工+完工
- 简单自动派单：从管辖该楼栋的工人中选当前在途单最少者，写入 dispatch_records；不做加权评分
- 全链路数据均按终版架构经过三库三服务，不写跨库代码
- H5 使用 Vant 实现宿管/工人两个入口

验收演示脚本：宿管登录 → 报修 → 工人登录看到工单 → 完工 → 宿管端状态变为已完成。

### P2：管理端与调度“血肉”

- F01 人员管理、F02 建筑管理、F03 类型字典、F04 派单规则配置（PC 完整页面）
- F17 升级为 skill/distance/load 加权派单；F16 工单去重
- 工单状态机补齐（待派→已派→维修中→完成/取消）
- F18 WebSocket：状态变化由 order-api 统一推送
- PC 工单总览从只读升级为可查看派单明细/日志
- F05 基础版：操作日志先同步写 order_db（不进 Kafka）

### P2 UI 设计主线（2026-09-08 确认，随功能同步实施）

- P2-UI-1 设计系统落地：主题色/字体层级/间距/状态色体系，PC 与 H5 各自布局模板与通用组件，不新增白名单外依赖。
- P2-UI-2 美化现有 P1 三端页面：登录页、宿管报修/工单列表、工人工单操作、PC 只读总览。
- P2-UI-3 P2 功能页随做随美：F01-F05/F16-F18 页面按设计系统直接实现，不搞“功能先行、外观后补”。

### P3：2D/3D 可视化

- F10 2D 总图（vue-konva）、F11 楼栋徽标、F13 钻取
- F12 2D→3D（Three.js 动态加载 + 低端降级）、F15 按类型批量完工
- fault_markers 与工单状态同步机制随本阶段联调

### P4：高级功能与论文收尾

- F19 Kafka 异步日志、F05 全量日志查询、F06 统计看板
- 演示数据完善、权限复核、论文截图/流程图/演示视频、部署文档

## 6. 开发纪律

- 每次 DB 结构变更：先改 02 DDL 与 `db/init` 迁移脚本，经人工确认后执行，不私自改表。
- 每个里程碑完成：更新本文件进度状态并提交（commit 遵循 AGENTS.md 格式）。
- 依赖版本冻结：P0 即锁定 go.mod/package-lock，之后不升级不换库。
