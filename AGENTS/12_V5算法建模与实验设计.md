# 12_V5 算法建模与实验设计（论文素材）

> 面向毕业设计论文"算法与实验"章节，覆盖 **V5.4 空间感知动态派单** 的全部模型与可复现实验。
> 所有数据均可通过项目现有接口复现（接口路径与实测样例见文末）。

## 1. 问题描述与符号

校园宿舍维修工单调度问题：给定一组待派工单 `O = {o₁…oₘ}` 与一组在岗工人 `W = {w₁…wₙ}`，
在满足"工种匹配、当班、未请假、账号启用"的约束下，为每个工单选择一名工人，
使**总代价最小**（技能匹配度高、通勤距离短、负载均衡）。

| 符号 | 含义 |
| --- | --- |
| `o.faultType` | 故障类型（electric / water / other），electric→需电工或通用，water→需水工或通用 |
| `w.jobType` | 工种：0 通用、1 电工、2 水工 |
| `w.baseBuilding` | 工人常驻楼栋 |
| `d(a,b)` | 建筑 a 与 b 的**路网最短路距离**（米），见第 2 节 |
| `load(w)` | 工人在途工单预计工时（分钟），无字段按 30 分钟/单 |
| `avgLoad` | 在岗候选人均负载 = Σload(w) / |C| |
| `skill(w,o)` | 技能匹配度 ∈ [0,1] |

## 2. 路网建模与距离计算

**建图**：区域概览中的 `road` 图元（支持跨格）铺成栅格，格点 4 邻接、边权 1 格（默认 1 格 = 10 米）。

**建筑接入**：`building` 图元优先取**与道路 4 邻接的边界格**为入口（gap = 0）；
若建筑与道路不相邻（实际绘制中很常见），取**离建筑矩形轮廓最近的道路格**为入口，
记步行格数 `gap(b) = d_Manhattan(b, r*)`。建筑 a、b 间距离：

```
d(a,b) = ( pathCells(r*_a, r*_b) + gap(a) + gap(b) ) × gridMeters
```

**算法**：边权相同 ⇒ 多源 BFS 即最短路，复杂度 `O(|B| × R)`（B 为建筑数、R 为道路格数），
实测 128 个道路格、4 栋建筑时单次构建 < 1 ms；结果按布局 JSON 内容缓存，布局变更自动重建。

**降级策略**：布局无道路时整体回退楼栋坐标欧氏距离，保证功能可用。

**实测（2026-09-15 真实布局）**：4 栋楼均接入路网、各距最近道路 2 格，最远通勤 150 米；
距离矩阵：1→3 = 60 米、2→4 = 100 米、2→3 = 130 米、3→4 = 130 米、1→2 = 150 米、1→4 = 150 米。
（对比：按楼栋坐标欧氏距离会得到不同的排序与数值，这正是实验一要验证的差异。）

## 3. 派单评分与批量指派

**候选集**：`C = { w | 当班(shift ≠ OFF) ∧ 工种匹配 ∧ 账号启用 ∧ 未请假 }`。

**单工单评分**（权重默认 0.4 / 0.3 / 0.3，可在"派单规则"页配置）：

```
score(w,o) = w_skill·skill(w,o) + w_dist·(1 − d(base(w), o.building)/d_max)
           + w_load·(1 − min(load(w), load_max)/load_max)
           − 0.5 · penalty(w)
penalty(w) = max(0, (load(w) − avgLoad) / avgLoad) , 仅当 load(w) > 1.2·avgLoad
```

其中 `d_max` 为路网距离矩阵最大值（无路网时用欧氏最大值），`load_max = maxConcurrent × 30`。
评分裁剪到 [0,1]。

**批量指派**：构造代价矩阵 `cost(w,o) = 1 − score(w,o)`，用**匈牙利算法**求最小总代价的一对一指派
（`adminbatchdispatchlogic`，工人槽位为"并发上限 + 2"的软上限，超出部分由 `penalty` 降权而非硬性拒派）。

**与 V4 的差异**：V4 距离因子用楼栋坐标欧氏距离、并有"达到并发上限即停派"的硬约束；
V5 改为路网最短路 + 动态负载惩罚（软约束）。

## 4. 双阈值保护机制

```
预警线： 待派工单数 > 在岗人数 × warnRatio(默认3)   ∨  最长等待 > warnHours(默认2) 小时
保护线： 待派工单数 > 在岗人数 × guardRatio(默认5)  ∨  最长等待 > guardHours(默认4) 小时
```

- 触发预警线：管理端高亮提醒，不改变派单行为；
- 触发保护线：**自动暂停自动派单**（写 `auto_dispatch_paused = 1`），新工单只入队，
  管理员处理积压后点"恢复自动派单"；
- 在岗人数为 0 时按 1 计算，语义为"无人可用 → 转人工"。

阈值判定实现为纯函数 `guardThresholds/guardLevelText`，单测覆盖 7 组边界用例（含"恰好等于阈值不触发"）。

## 5. 事件驱动重算

触发事件：新工单、完工、解锁、手动改派、排班保存/生成、请假登记/审批/撤销。
统一入口 `TriggerDispatchRecheck`，**1.5 秒防抖**；另有 **60 秒兜底扫描**处理漏派：
非保护模式下对待派队列执行一次批量指派，并顺带评估保护线。

实测日志：`dispatch loop started, interval=1m0s`；完工事件触发后
`dispatch recheck(event): dispatched=1 remained=0`（对应工单在下一次评估中被自动派给在岗工人）。

## 6. 实验设计（三组对比）

> 统一环境：`docker compose up -d`，管理端 `admin/admin123`；构造场景用宿管账号 `dorm1`（1 号楼）建单，
> 用工人账号 `worker1~4` 开工/完工控制负载，用管理端接口读指标。

### 实验一：欧氏距离 vs 路网距离
- **变量**：距离因子计算方式（V4 欧氏 / V5 路网）。
- **构造**：在区域概览中绘制"建筑不与道路相邻"的布局（本项目实测场景：建筑距道路 2 格），
  保证两种方式给出的距离排序不同。
- **指标**：`Σ d(w.base, o.building)`（总通勤距离）、跨楼栋派单次数、平均**路网**通勤距离（同一指标下对比）。
- **数据来源**：`GET /api/admin/campus-layout/distances`（路网矩阵）、`GET /api/admin/orders`（派单结果）。

### 实验二：有 / 无动态负载均衡
- **变量**：是否启用负载惩罚（`load_weight` 置 0 或 0.3，惩罚系数 0.5 或 0）。
- **构造**：保持 4 名工人、制造 20+ 张待派工单的积压场景（保护线可临时调高避免中断）。
- **指标**：负载标准差 `σ(load)`、最大在途工单数、平均等待时长（`待派开始 → 派出`）。
- **数据来源**：`GET /api/admin/worker-board`（各工人 `activeOrders`/`loadMinutes`/`loadDeviation`）。
- **实测样例**（当前数据，未开对比实验）：李工 +181%、其余 −56%/−56%/−70%，说明单点过载可由惩罚权重调节。

### 实验三：有 / 无双阈值保护
- **变量**：阈值是否启用（保护线置为极大值 = 关闭）。
- **构造**：短时间内批量建单（或降低 `backlog_guard_ratio`）制造积压。
- **指标**：超时未派工单占比、最长等待时长、保护模式触发次数、人工介入次数。
- **数据来源**：`GET /api/admin/dispatch-guard`（`pendingCount`、`longestWaitMinutes`、`level`、`mode`）。

### 实验复现要点（已实测）
- 阈值纯函数单测：`cd services/order && go test ./internal/logic/ -run Guard -v`（7 组用例）；
- 路网单测：`go test ./internal/logic/ -run RoadNetwork -v`（相邻 60 米、gap 5 格 100~110 米、降级为 nil）；
- 保护模式验证：`update order_db.dispatch_rule_config set rule_value = 1 where rule_key = 'auto_dispatch_paused'`
  后建单 → 工单停留在"待派单"；调用 `POST /api/admin/dispatch-guard/resume` → 恢复自动派单并可批量派出。
