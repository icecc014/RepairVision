# 11_V5规划与任务设计.md（2026-09-15 拟定）

> 版本定位：**V5「空间感知的智能派单与排班优化」**
> 本文档先给出总任务与分阶段阶梯计划，再给出关键技术设计，作为 V5 各阶段开工与验收的依据。
> 需求来源：用户 2026-09-15 提出的六部分需求（区域概览、排班与工时、动态派单与路径规划、任务均衡与自动派单、整体目标、其他）。

## 1. 总任务

在 V4 已完成的"工单闭环 + 楼层二三维可视化 + 请假感知排班"基础上，新增**校园/建筑群级别的空间数据（区域概览）**，并据此升级排班与派单：

1. **空间基础**：把现有楼层布局设计器泛化为通用画布，用于绘制校园/园区总平面图（建筑、道路、广场等图元），为派单提供建筑坐标与路网连通关系；
2. **时间基础**：排班改为**双休 + 仅白班**（上午、下午两个工作时段可配置），派单与工作时段解耦，非工作时段工单进入队列；
3. **人员基础**：工人分为**电工与水工**两类，宿管报修时按"电维修 / 水维修"选择，其他类型不自动派单，转由管理员协商或外援；
4. **算法升级**：动态派单以**当前在岗工人**为候选集，结合**路网距离、工种匹配、动态负载均衡**计算代价，批量场景用匈牙利算法求最小总代价，并支持事件驱动的自动重算与积压告警；
5. **管理可干预**：管理端可查看自动派单结果、手动转派、调整优先级与锁定分配，异常情况可控。

**最终目标**：减少无效移动与跨区往返、避免工单积压与分配不均、降低管理端实时干预成本、提升维修效率与工人对建筑群布局的认识。

## 4. 分阶段阶梯任务

### V5.1 区域概览（校园平面图）— 空间数据基础
**目标**：管理端能绘制并保存校园/建筑群总平面图，三端可查看。

功能点：
1. 通用画布抽象：从 `LayoutDesigner.vue` 抽出网格模型、碰撞检测、撤销栈、属性面板逻辑，形成可复用组件（楼层布局与区域概览共用）；
2. 图元类型：建筑、道路、广场/绿地、校门/出入口、自定义（可命名）；每种图元有独立配色与图标；
3. 建筑图元两种来源：关联"建筑信息管理"中的楼栋（带出名称与编号）或自定义名称（食堂、医院、体育馆等）；
4. 画布规模：支持更大的网格（默认 40×30，可调至 60×40）与缩放、平移；
5. 存储：`map_db` 新增 `campus_layouts` 表（支持多张图，默认图唯一）；
6. 展示：管理端"区域概览"页（编辑 + 预览）；宿管端与工人端新增只读"校园概览"视图；
7. 保存校验：建筑图元必须命名、道路图元需连通（至少与其他图元接壤），无重叠。

数据与接口：`GET/POST/PUT /api/admin/campus-layout`；`GET /api/worker/campus-map`（宿管与工人共用的只读接口）。
验收：绘制含 4 栋宿舍楼 + 食堂 + 2 条道路的平面图并保存；三端均能正确显示；刷新后不丢失。

### V5.2 工种分类与报修类型治理
**目标**：明确"谁修什么"，其他类型不自动派单。

功能点：
1. 用户表新增 `job_type`（1=电工，2=水工，0=通用）；人员管理中可设置；
2. 故障类型字典新增 `category`（electric / water / other）与 `auto_dispatch`（是否自动派单）；
3. 宿管报修界面：故障类型按"电维修 / 水维修 / 其他"分组，选择后自动带出类别；
4. 派单时按类别筛选候选工人（电工修电、水工修水，通用工人可接两类）；
5. 其他类型工单：不进入自动派单，状态标记"待管理员处置"，管理端列表高亮并提示"协商派单 / 寻求外援"；
6. 管理端可手动物色电工/水工或外部人员完成任务并记录。

数据与接口：`worker_db.users` 增字段；`order_db.fault_types` 增两字段；工单新增"待处置"标记字段或复用 `pending_reason`；管理端新增"待处置工单"筛选。
验收：宿管提交"电维修"工单只派给电工；提交"其他"类型工单不自动派单并出现在管理端待处置列表；管理员可手动指派完成。

### V5.3 双休白班排班改造
**目标**：排班符合"双休 + 仅白班"的实际作息，并提供在岗判断。

功能点：
1. 班次类型简化为"白班 / 休息"（历史午/晚班数据保留但界面不再提供）；
2. 每周休息天数默认 2，支持 0~3；支持两种模式：固定休息日（如周六、周日）与错峰轮休（按楼栋保障代价函数择优，沿用 V4 算法）；
3. 工作时段配置：上午上班/下班、下午上班/下班（默认 08:00–12:00、14:00–18:00），可在系统设置中修改；
4. 在岗判断接口：给定时间点与工人，返回是否在岗（今日白班 ∧ 时段内 ∧ 未请假 ∧ 启用）；
5. 排班页展示：每日在岗人数、休息人数、请假人数，以及"当前在岗 N 人"的实时提示；
6. 派单解耦：非工作时段仍可生成与分配工单，工人开工动作受时段约束（非时段内开工给出提示或拒绝，可配置）。

数据与接口：`worker_db.worker_schedules` 班次取值收敛；新增系统配置表或沿用派单规则表存工作时段；`GET /api/worker/duty-status`。
验收：生成排班后每人每周恰好休 2 天；界面只出现"白班/休息"；非工作时段派单成功但工单处于"待开工"；上班后按在岗工人重算派单。

### V5.4 空间感知的动态派单与负载均衡（核心）
**目标**：以在岗工人为候选集，结合路网距离与动态负载，自动、均衡地派单。

功能点：
1. 路网距离：由区域概览的道路图元构建栅格图，建筑图元接入最近道路节点；用 Dijkstra 计算建筑间最短路，缓存 N×N 距离矩阵（布局变更时失效重建）；
2. 候选集：在岗 ∧ 工种匹配 ∧ 账号启用的工人；
3. 评分：技能匹配 40% + 路网距离 30% + 负载 30%（权重可配置）；同楼栋加成、跨区惩罚；
4. 优先级：紧急/超时/等待时长长的工单优先（等待时长因子），超时工单插队；
5. 动态负载均衡：人均负载 = 待派工单数 / 在岗人数；对负载 > 人均×1.2 的工人施加惩罚权重；批量指派用匈牙利算法最小化总代价（代价 = 1 − 评分 + 负载偏离惩罚）；
6. 取消硬性并发上限：不再因"达到上限"而停止派单，改为权重惩罚与告警；
7. 事件驱动重算：新工单创建、工单完工、上下班切换、请假生效/撤销、临时调班、手动调整 → 触发重算（防抖 1~3 秒）；
8. 积压告警：待派工单数超过"在岗人数 × 阈值"或存在超过 X 小时未派出的工单 → 管理端告警并给出建议（增援/调整排班/外援/手动干预）；
9. 管理端干预：派单结果面板，支持手动转派、调整优先级、锁定（某单不自动改派 / 某工人不参与本轮调整）。

数据与接口：`order_db` 新增执行计划字段（预计到达时间等，可选）；新增 `GET /api/admin/dispatch-plan`、`POST /api/admin/dispatch/recalc`、`POST /api/admin/orders/:id/lock`。
验收：构造"4 名工人（2 电 2 水）+ 8 张工单 + 路网"的场景，验证：只派给在岗且工种匹配的工人；批量派单总距离明显小于逐单贪心；负载分布标准差下降；超时工单被优先处理；新工单加入后自动重算。

### V5.5 管理端干预完善、回归与收尾
**目标**：异常可控、全量回归、文档与论文素材同步。

功能点：
1. 派单结果看板：按工人展示在途工单、预计工时、负载偏离度、当前所在楼栋（来自最近完成工单）；
2. 异常处理：待处置工单（其他类型）、超时未派、无可用工人等场景的人工处理入口；
3. 区域概览与派单联动演示：修改路网后距离矩阵重建并影响派单；
4. 回归：三端接口冒烟、算法单测（距离矩阵、评分、匈牙利、负载均衡、在岗判断）、前后端构建与静态检查；
5. 文档：更新 V5 完成记录、论文算法素材（空间感知派单的建模与实验设计）。

验收：全套回归通过，形成"区域概览 → 在岗判断 → 路网距离 → 负载均衡 → 自动派单 → 管理干预"的完整演示动线。

## 5. 关键技术设计

### 5.1 区域概览数据模型（campus layout）

```json
{
  "version": 1,
  "cols": 40, "rows": 30,
  "blocks": [
    { "id": "b1", "kind": "building", "row": 4,  "col": 6,  "rowSpan": 4, "colSpan": 6,
      "buildingId": 1, "label": "1号宿舍楼" },
    { "id": "b2", "kind": "building", "row": 4,  "col": 22, "rowSpan": 4, "colSpan": 6,
      "label": "第二食堂", "customBuilding": true },
    { "id": "r1", "kind": "road",     "row": 12, "col": 0,  "rowSpan": 1, "colSpan": 40 },
    { "id": "g1", "kind": "gate",     "row": 0,  "col": 18, "rowSpan": 1, "colSpan": 3, "label": "南门" }
  ]
}
```

- 图元 `kind`：`building`（建筑）/ `road`（道路）/ `green`（广场绿地）/ `gate`（校门）/ `custom`（自定义）；
- 复用 V4 的整数格模型、逐格试探碰撞检测与撤销栈；网格上限提高到 60×40；
- 存储：`map_db.campus_layouts(id, name, is_default, cols, rows, layout_json, updated_at)`，默认图唯一；由 map 服务通过 RPC 暴露给 order 服务与前端。

### 5.2 路网模型与距离计算

1. **建图**：道路格 → 栅格节点（4 邻接），边权 = 1 格；建筑图元找出其边界上"与道路格 4 邻接"的格作为**入口节点**（多个入口取最短者）；
2. **最短路**：以每栋建筑的入口为源点跑一次 Dijkstra，得到建筑间最短路（格数）；距离（米）= 格数 × 格边长（默认 10 米，可配置）；
3. **缓存**：N 栋建筑的距离矩阵（N ≤ 60），布局保存后重建并落 Redis 缓存；
4. **复杂度**：O(N × R log R)，R 为道路格数（≤ 2400），单次重建 < 50ms；
5. 未接入道路的建筑（孤立图元）：退化为欧氏距离并给出提示。

### 5.3 派单算法升级（V5.4 核心）

```
候选集 C = { w | 在岗(w) ∧ 工种匹配(w, order) ∧ 账号启用(w) }
人均负载 avg = 待派工单数 / |C|
score(w, o) = 0.4×技能 + 0.3×(1 − 距离归一化) + 0.3×(1 − 负载偏离)
负载偏离(w) = max(0, 负载(w) − avg) / max(1, avg)      # 高于均值才有惩罚
同楼栋加成 = +0.1（同栋） / +0.05（相邻楼栋且路网距离 < 2 格）
紧急度 = 超时 +0.15；等待时长每超 30 分钟 +0.05（上限 +0.3）
cost(w, o) = 1 − clamp(score) + 0.5×负载偏离(w)
批量：min Σ cost(w, o) s.t. 匈牙利算法一对一指派（无硬性并发上限）
```

- 事件驱动：`new_order` / `order_done` / `duty_change` / `leave_change` / `manual_adjust` 触发重算，1~3 秒防抖；
- 自动派单常驻：定时（如 60 秒）兜底扫描，处理漏派与积压；
- 告警阈值：待派 > 在岗人数 × 3，或存在等待 > 2 小时未派出的工单。

### 5.4 排班改造（V5.3）

- 班次：`DAY`（白班）/ `OFF`（休息）；工作时段由配置项 `work_morning(08:00-12:00)`、`work_afternoon(14:00-18:00)` 描述；
- 双休：`rest_days_per_week = 2`（默认），模式 `fixed`（固定周六周日）或 `staggered`（错峰，沿用 V4 代价函数，加入"楼栋在岗保障"）；
- 在岗判断：`is_on_duty(worker, ts) = 今日排班=DAY ∧ ts ∈ 任一工作时段 ∧ 当日无已批准请假 ∧ 账号启用`；
- 与派单解耦：派单不受时段限制；`开工` 动作受时段约束（默认提示但允许强制开工，可配置为拒绝）。

### 5.5 工种与其他类型处置（V5.2）

- `worker_db.users.job_type`：1=电工，2=水工，0=通用；
- `order_db.fault_types.category`：electric / water / other；`auto_dispatch`：1/0；
- 宿管报修页按"电维修 / 水维修 / 其他"分组选择；

- **数据兼容**：V4 的楼层布局数据（layout_json v2）保持不变；校园概览使用新表，互不影响；
- **班次兼容**：历史排班中的 MORNING / AFTERNOON 记录保留展示为"白班（历史）"，新生成排班只写 DAY/OFF；
- **派单兼容**：无区域概览数据时，距离因子退化为楼栋坐标欧氏距离，保证功能可用；
- **性能**：距离矩阵缓存 + 防抖重算，避免高频事件导致重复计算；批量指派规模上限（工单 ≤ 100、工人 ≤ 50）保证毫秒级返回；
- **可解释性**：派单结果需展示各因子得分与最终代价，便于答辩演示与问题排查。

### 10.1 双阈值保护机制（用户新增要求）

在取消硬上限的同时，保留两条可配置阈值形成"预警—保护"两级机制：

| 阈值 | 触发条件（可配置） | 系统行为 |
| --- | --- | --- |
| **预警线** | 待派工单数 > 在岗人数 × 3，或存在等待超过 2 小时未派出的工单 | 管理端高亮提醒（调度看板 + 工单总览角标），不改变自动派单行为 |
| **保护线** | 待派工单数 > 在岗人数 × 5，或存在等待超过 4 小时未派出的工单 | **暂停自动派单**，切换为"人工处置模式"：新工单只入队不自动分配，管理端收到高优先级告警与处理建议（增援 / 调班 / 外援 / 手动指派），处理完毕后点击"恢复自动派单" |

- 两条阈值均可在"派单规则配置"页调整（默认 3 和 5），保护线必须大于预警线；
- 进入保护模式与退出保护模式都会写入操作日志，并在管理端顶部展示当前模式（自动 / 人工）；
- 保护模式下仍允许管理端手动派单与改派，工人端不受影响。

### 10.2 实施口径调整（区域概览存储位置）

为降低 V5.1 的跨服务改动成本，区域概览数据先由 **order 服务托管在 `order_db.campus_layouts`**（对外仍提供 `/api/admin/campus-layout` 与 `/api/worker/campus-map`），布局 JSON 内通过 `buildingId` 关联楼栋、并保留 `label` 冗余名称：

- 优点：无需改动 map/worker 服务的 proto 与 RPC，可最快让三端看到效果；
- 后续如需迁移到 map 服务，只需把 store 层实现替换为 map RPC 调用，接口与数据模型不变（表结构与 JSON 格式保持一致即可平滑迁移）。

### 16.3 关键算法修复：建筑与道路不相邻时也能走路网

**发现的问题**：示例布局中建筑与道路之间存在间隙（如建筑行 4–8、道路行 13），原实现要求"建筑与道路 4 邻接"才算接入，导致**所有建筑被判为未接入路网，派单距离实际全部回退到欧氏距离**——V5.4 的路网距离形同虚设。

**修复**：建图改为"相邻优先 + 最近道路格兜底"：
- 建筑与道路相邻时，gap = 0（原行为不变）；
- 不相邻时，取**离建筑轮廓最近的道路格**作为入口，把这段步行格数记为 `gap`，建筑间距离 = `(路网格数 + gap(from) + gap(to)) × 10 米`；
- 新增 `GapCells()` 供前端展示"距最近道路 X 格"；只有布局中完全没有道路时才回退欧氏距离。
- 单测：新增 `TestBuildRoadNetworkConnectsByGap`（gap=5 格、距离 100~110 米），原相邻用例（60 米）与降级用例保持通过。
