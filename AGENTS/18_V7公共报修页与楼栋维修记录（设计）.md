# V7 公共报修页与楼栋维修记录（设计任务书）

> 来源：2026-09-17 需求（学生/教师无需登录直接报修 + 进度查询 + 本地历史快捷入口 + 防刷），并保留宿管端“整栋楼维修记录”能力。
> 现状基线：V6.0（28 栋楼 / 10 名工人 / 三端可用 / 区域概览与空间感知派单已完成）。

## 1. 需求基线与设计映射

| 需求点 | 设计落点 |
| --- | --- |
| 无需登录直接访问 `/report` | mobile-web 内新增公开路由 `/report`（路由守卫放行）+ Nginx `location /report`，并新增宿主端口 8081 作为独立公共入口 |
| 微信内置浏览器可打开 | 纯 H5（Vue3 + Vant），无 App 依赖、无扫码、无强制绑定；不自动定位房间 |
| 每次独立填写 | 表单不预填房间，只有用户点“历史卡片”才填充楼栋 + 房间号 |
| 历史记录缓存 | `localStorage['repair_history']`，最多 10 条、去重置顶、可“清除历史” |
| 提交报修 | `POST /api/public/report`（楼栋 / 房间号 / 故障类型 / 描述 / 报修人身份 / 联系人 / 验证码） |
| 查询进度 | `GET /api/public/room-orders?buildingId&room`，展示类型 / 状态 / 提交时间 / 工人姓名，查询不缓存 |
| 防刷 | 图形验证码 + 同房间 30 分钟限流 + IP 每分钟 3 次 + 3 天内同类合并 + 敏感词过滤 |
| 宿管端楼栋维修记录 | 保持并增强：本栋工单列表继续可用，新增“来源 / 报修人身份”标记与本栋维修记录统计条 |

## 2. 现状盘点（能复用什么、缺什么）

可直接复用：

- 合并去重机制已存在：`orders.is_merged`（0 独立 / 1 主单 / 2 子单）、`orders.main_order_id`、`order_duplicate_records`；
- 房间合法性校验 `validateRoomForBuilding`（房号与楼层 / 每层房间数一致）；
- 故障类型字典 `fault_types`（code / name / category / auto_dispatch）与建单后自动派单引擎（工种过滤、路网距离、双阈值保护）；
- 宿管端 `DormView.vue` 已按 `building_id` 展示本栋工单列表（即“整栋维修记录”雏形）；
- go-zero 自带 `core/stores/redis`（go.mod 已含 go-zero v1.7.2），无需新增依赖。

当前缺口：

1. 现有路由分组均为 `RoleGuard(1/2/3)`，需要新增 `/api/public/*` 免鉴权路由；
2. `orders.reporter_id` 为 `NOT NULL`（宿管 ID），公共报修没有登录用户，需要允许 0 并补充报修人身份字段；
3. `orders.source` 只有 `dormitory/admin`，需要扩展 `public`；
4. Redis 容器已编排但代码未接入，V7 首次真正接入（验证码 + 限流），并保留降级方案；
5. 无验证码、无限流、无敏感词过滤能力；
6. 移动端无公开路由与页面，Nginx 无 `/report` 入口。

## 3. 总体设计

```text
学生 / 教师（微信或浏览器）
        │  http://<host>:8081/report   （公共入口，无需登录）
        ▼
   Nginx（web 容器）
     /report       → mobile-web 静态资源（SPA fallback）
     /api/public/* → order-api:8888（免 JWT 公开分组）
        ▼
   order-api
     ├─ 验证码校验 / 限流 / 敏感词（Redis）
     ├─ 3 天内同类合并（order_duplicate_records + main_order_id）
     ├─ 建单（source=public, reporter_id=0, reporter_type, reporter_contact）
     └─ 复用既有派单引擎（工种过滤 + 路网距离 + 负载 + 双阈值保护）
        ▼
   MySQL(order_db) ←→ Redis(验证码/限流) → Kafka(操作日志)
        ▼
   宿管端：本栋工单列表（含来源标记与本栋维修记录统计）
   管理端：报修记录页（来源列 + 筛选）
```

## 4. 数据库变更（db/migrations/20260917_v7_public_report.sql）

```sql
alter table order_db.orders
  add column reporter_type tinyint not null default 0 comment '0 宿管 1 学生 2 教师 3 其他',
  add column reporter_contact varchar(32) null comment '报修人联系方式（选填）',
  modify column reporter_id bigint not null default 0 comment '宿管用户ID；公共报修为 0';

alter table order_db.orders add key idx_room_created (building_id, room, created_at);

create table if not exists order_db.sensitive_words (
  id bigint auto_increment primary key,
  word varchar(32) not null unique,
  created_at datetime default current_timestamp
) engine=InnoDB default charset=utf8mb4;
```

说明：`source` 为 varchar，新增取值 `public` 无需改结构；历史宿管报修数据不受影响（`reporter_type=0`、`source=dormitory`）。

## 5. 接口设计（全部免 JWT，走公开限流）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/public/captcha` | 获取图形验证码（SVG + captchaId，有效 5 分钟、一次性） |
| GET | `/api/public/buildings` | 公开楼栋列表（仅 id / code / name，供下拉框） |
| POST | `/api/public/report` | 提交报修（校验验证码 → 限流 → 敏感词 → 合并去重 → 建单 → 触发派单） |
| GET | `/api/public/room-orders` | 按楼栋 + 房间号查询该房间工单（脱敏，按时间倒序，最多 20 条） |

提交请求示例：

```json
{
  "buildingId": 1, "room": "211", "faultType": "electric",
  "description": "电灯不亮，开关有火花", "reporterType": 1,
  "contact": "138****0000", "captchaId": "c_8f21", "captchaCode": "7K3P"
}
```

提交响应场景：

| 场景 | code | msg / data |
| --- | --- | --- |
| 提交成功 | 0 | `{orderNo, status, dispatched, workerName?}` + “报修已提交，等待处理” |
| 已合并 | 0 | `{merged:true, mainOrderNo}` + “该房间相同类型报修已在处理中，已并入工单 XXX” |
| 验证码错误 | 400 | “验证码错误或已过期，请重新获取” |
| 同房间限流 | 429 | “该房间 30 分钟内已提交过报修，请稍后再试” |
| IP 限流 | 429 | “提交过于频繁，请稍后再试” |
| 敏感词 | 400 | “描述包含不允许的词汇，请修改后重试” |
| 房间非法 | 400 | “房间号与该楼栋不匹配” |

查询响应（脱敏：不含联系方式与内部评分字段）：

```json
{ "code": 0, "data": { "buildingName": "1号宿舍楼", "room": "211", "orders": [
  { "faultTypeName": "电维修", "description": "电灯不亮", "statusText": "已完成",
    "createdAt": "2026-09-15 10:30", "completedAt": "2026-09-15 14:20", "workerName": "电工·孙师傅" }
] } }
```

## 6. 防刷与安全设计

| 机制 | 规则 | 实现 |
| --- | --- | --- |
| 图形验证码 | 提交必填、一次性 | 服务端生成 4 位字符（去易混淆字符），用 SVG 文本渲染（不引入图像字体依赖），`captcha:{id}` 存 Redis，TTL 300s，校验后删除 |
| 同房间限流 | 30 分钟 1 次 | Redis `INCR rl:room:{buildingId}:{room}` + `EXPIRE 1800` |
| IP 限流 | 每分钟 3 次 | Redis `INCR rl:ip:{ip}` + `EXPIRE 60`（IP 由 Nginx `X-Real-IP` 透传） |
| 3 天内同类合并 | 同楼栋 + 同房间 + 同类型 + 3 天且主单未完成 | 复用 `order_duplicate_records`：不新建主单，写合并记录并返回主单号 |
| 敏感词过滤 | 脏话 / 广告 | `sensitive_words` 表（管理员可维护），命中直接拒绝 |
| 输入约束 | 描述 5~200 字、房间号必须匹配楼栋、联系人 ≤ 32 字 | 前后端双重校验 |
| 隐私 | 查询只返回类型/描述/状态/时间/工人姓名 | 不返回联系方式与内部评分 |
| Redis 降级 | Redis 不可用时改用进程内 TTL 缓存 | 验证码与限流仍生效（单实例部署可接受） |

## 7. 前端设计（frontend/mobile-web/src/views/PublicReportView.vue）

- 路由：`/report`，`meta: { public: true }`，路由守卫放行（现有守卫只拦 requiresAuth）；
- 页面结构：两个 Tab —— 我要报修 / 查询进度；
- 报修表单：楼栋（下拉，来源 `/api/public/buildings`）→ 房间号 → 故障类型（电维修 / 水维修 / 其他维修，映射 electric / water / other）→ 故障描述（多行 + 字数）→ 报修人身份（学生 / 教师 / 其他）→ 联系人（选填）→ 图形验证码（点击刷新）→ 提交；
- 历史卡片：表单上方横向滚动卡片（楼栋 + 房间号），点击只填充楼栋与房间号，不自动提交、不自动定位；右侧“清除历史”；无记录时不显示该区域；
- 提交反馈：成功 / 已合并 / 验证码错误 / 限流 / 敏感词，按 code 与 msg 展示；成功后把“楼栋+房间”写入 localStorage（去重置顶、最多 10 条）；
- 查询页：楼栋 + 房间号 → 结果卡片（类型 / 状态色标 / 提交时间 / 完成时间 / 工人姓名），空态提示“该房间暂无报修记录”；
- 适配：沿用现有 postcss-px-to-viewport；目标浏览器含微信内置 WebView；
- 本地缓存：`saveHistory / getHistory / clearHistory`，key = `repair_history`。

## 8. 与宿管端 / 管理端的协同

- 宿管端（`/m/dorm` 本栋工单）：
  1. 公共报修与宿管报修同表同 `building_id`，自动出现在本栋列表；
  2. 列表项新增来源徽标：`公共报修·学生` / `公共报修·教师` / `宿管报修`（依据 source + reporter_type）；
  3. 顶部新增“本栋维修记录”统计条：总数 / 待处理 / 维修中 / 已完成（当前时间窗）+ 按故障类型计数；
  4. 筛选器增加“来源”维度（全部 / 宿管报修 / 公共报修）。
- 管理端：报修记录台账与工单总览增加“来源”列与筛选，用于统计公共渠道占比与响应时长（论文素材）。

## 9. 访问入口与 Nginx

```nginx
# 公共报修页（无需登录）
location /report {
    alias /usr/share/nginx/html/m/;
    try_files $uri $uri/ /report/index.html;
}
```

说明：本项目 web 镜像把移动端产物放在 `/usr/share/nginx/html/m`（非需求稿里的 mobile-web 路径），因此用 alias 指向 `m/`；
`docker-compose.yml` 的 web 服务新增端口映射 `8081:80`，形成独立公共入口 `http://<host>:8081/report`；原 8080 的管理端与移动端入口不变，两个端口共用同一 Nginx 与前端产物。

## 11. 风险与待确认决策

1. 8081 端口：本机演示默认占用 8081，若与校内环境冲突可改端口或只保留 `/report` 路径（两条入口共用同一 Nginx，切换成本极低）；
2. 公开查询的隐私边界：按“楼栋 + 房间号”即可查询进度，是便捷与隐私的权衡；已做脱敏，如需更严可要求输入报修时留的联系人后 4 位（默认不做）；
3. 合并语义：需求写“3 天内同类合并”，实现为“不新建主单，把新报修并到已有主单并提示主单号”，比直接拦截更符合“合并”语义，也避免重复派单；
4. reporter_id = 0：公共报修不再关联宿管用户；通知链路对 reporter_id = 0 跳过推送（宿管仍能在本栋列表看到）；
5. 验证码形式：采用 SVG 文本验证码（零新增依赖，答辩可说明为自研轻量实现），如需更复杂可后续替换为图片验证码。

## 12. 论文可用素材

- 公共报修渠道的“无登录 + 历史缓存 + 防刷”设计（验证码、IP/房间双维度限流、同类合并）可写入“非功能需求与安全设计”；
- 复用 `order_duplicate_records` 的合并去重可量化“重复报修率”与“合并节省的派单次数”；
- 公共渠道与管理渠道的占比、响应时长对比可作统计分析素材。
