# V6.3 派单保护线口径修正 + 派单规则可视化编辑 任务书

> 来源：2026-09-16 用户反馈（调度看板"3 单就暂停派单"、派单规则配置不可编辑/新增无效）

## 1. 问题诊断（先说结论）

**"3 单就暂停派单"不是软上限（8+2=10）造成的**，而是**双阈值保护线**：

1. 保护线条件之一是"存在等待超过 `backlog_guard_hours`(4 小时) 未派出的工单"——与单量无关。
   测试数据里存在创建于数小时前的待派工单，`PendingBacklog` 取的是**最老待派单的等待分钟数**，
   于是刚有 2~3 单待派，等待时长就已经超过 4 小时 → 触发保护线；
2. 触发后写 `dispatch_rule_config.auto_dispatch_paused = 1`，**并且不会被自动恢复**（今天 19:13 就是这种情况，
   现在库里仍是暂停态），所以之后的新工单只入队、不派单 → 看板上看起来"3 单就停了"。
3. 另外旧口径 `待派 > 在岗 × 5`：当只有 1 人在岗（比如只有 1 个工人正处于白班时段）时，
   6 单就会触发保护线，对"大学校园一天几十单"的场景太敏感。

**剩下的任务怎么办（本次一并解决）**：

- 保护线触发后工单继续入队，管理员可在「调度看板 / 工单总览」用**手动批量派单**立即派出去；
- 新增**自动恢复**：每次评估时若指标回落到预警线以下，自动恢复自动派单（不再"一次积压永久停摆"）；
- 点「恢复自动派单」后**立即触发一次派单重算**，积压单马上被派出去，而不用等 60 秒兜底扫描。

## 2. 保护线口径重做（V6.3）

### 2.1 新判定公式（绝对单量 + 人均倍数取较大者）

```
预警线：待派 ≥ max(在岗人数 × warn_ratio, warn_min_orders)   或   最长等待 > warn_hours
保护线：待派 ≥ max(在岗人数 × guard_ratio, guard_min_orders) 或   最长等待 > guard_hours
```

### 2.2 新默认值（放宽，均可在线修改）

| 规则 | 旧默认 | 新默认 | 含义 |
| --- | --- | --- | --- |
| `backlog_warn_min_orders` | （无） | **10** | 预警线绝对下限：待派 ≥ 10 单 |
| `backlog_guard_min_orders` | （无） | **20** | 保护线绝对下限：待派 ≥ 20 单 |
| `backlog_warn_ratio` | 3 | **5** | 人多时按 在岗 × 5 预警 |
| `backlog_guard_ratio` | 5 | **10** | 人多时按 在岗 × 10 保护 |
| `backlog_warn_hours` | 2 | **6** | 最长等待 > 6 小时才预警 |
| `backlog_guard_hours` | 4 | **12** | 最长等待 > 12 小时才暂停自动派单 |

效果：在岗 1 人 → 10 单预警 / 20 单保护；在岗 4 人 → 20 单预警 / 40 单保护；在岗 10 人 → 50 单预警 / 100 单保护。

### 2.3 自动恢复与立即重算

- `evaluateDispatchGuard` 增加：暂停态且**未触预警线**时自动 `auto_dispatch_paused = 0` 并写日志；
- `POST /api/admin/dispatch-guard/resume` 恢复后立即 `TriggerDispatchRecheck`，积压单当场派出去；
- 看板展示：待派 / 在岗 / 最长等待 / 当前阈值 + 暂停原因 + 「恢复自动派单」按钮。

## 3. 派单规则配置可视化编辑（V6.3）

### 3.1 根因

现在页面是"裸表 + 自由填 rule_key"，而**引擎只认自己代码里的固定 key**，
所以新增任意 key 不会生效；编辑框还把值限制在 0~1（小时/倍数类规则根本改不了）。

### 3.2 设计：规则注册表（元数据驱动）

后端维护**规则注册表**：key、中文名、分组、类型（number/bool）、单位、取值范围、步长、精度、
默认值、说明、是否运行态只读、引擎是否使用。前端按元数据渲染表单，**保存即写库、引擎每次派单读库，无需重启**。

分组：

| 分组 | 规则 |
| --- | --- |
| 评分权重 | `skill_weight` `distance_weight` `load_weight` |
| 自动派单 | `auto_dispatch_enabled` |
| 超时提醒 | `pending_timeout_hours` `dispatched_timeout_hours` |
| 积压保护 | `backlog_warn_min_orders` `backlog_warn_ratio` `backlog_warn_hours` `backlog_guard_min_orders` `backlog_guard_ratio` `backlog_guard_hours` |
| 运行状态（只读） | `auto_dispatch_paused` |

### 3.3 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/admin/dispatch-rules` | 返回 `{groups, paused, pending, onDuty, updatedAt}`（含未落库的注册规则，值取默认值） |
| PUT | `/api/admin/dispatch-rules` | 批量保存 `{items:[{key,value,enabled}]}`，按元数据校验范围，禁止改运行态规则 |
| POST | `/api/admin/dispatch-rules` | 新增规则：已注册未使用的 key 直接补录；自定义 key 需符合 `^[a-z][a-z0-9_]{2,31}$` 并标注"引擎暂不支持" |
| POST | `/api/admin/dispatch-rules/:key/reset` | 恢复该规则默认值 |
| DELETE | `/api/admin/dispatch-rules/:key` | 删除（仅自定义规则） |

### 3.4 前端

- 分组卡片：中文名 + 说明 + 控件（数字框带单位/范围、开关）+ 启用开关 + 「恢复默认」；
- 顶部：`保存修改`（批量）、`全部恢复默认`、运行态横幅（是否暂停 + 恢复自动派单）；
- 新增规则对话框：先展示"已注册但还没落库的规则"清单可直接勾选补录；自定义规则需填 key/类型/值/说明，并明确提示"未注册的自定义规则不会影响派单引擎"。

## 5. 实现补充（口径微调，2026-09-16 晚）

### 5.1 保护线只看「待派单量」，等待时长只提醒
实施中发现按"等待时长"触发暂停会把**最该被派出去的积压单**卡住（暂停→不派→等更久）。最终口径：

- 预警线：待派 ≥ max(在岗×warn_ratio, warn_min_orders) **或** 最长等待 > warn_hours（只提醒，不停派单）；
- 保护线（暂停自动派单）：**只看** 待派 ≥ max(在岗×guard_ratio, guard_min_orders)；
- 自动恢复：待派回落到保护线以下即自动恢复；暂停期间若仍有工单等待 > guard_hours（默认 12 小时）则**强制恢复**并把积压派出去；
- 手动「恢复自动派单」会立即触发一次派单重算，不等 60 秒兜底扫描。

### 5.2 实测（本机 2026-09-16 19:5x）

| 项 | 结果 |
| --- | --- |
| 迁移后规则值 | warn: min 10 单 / ratio 5 / hours 6；guard: min 20 单 / ratio 10 / hours 12 |
| 暂停态自愈 | 日志 `dispatch guard auto resumed: pending=3 onDuty=0 waitMinutes=651`，规则值回到 0 |
| 积压派单 | 下一个兜底扫描 `dispatch recheck(ticker): dispatched=3 remained=0`，待派清零 |
| 规则接口 | `GET /api/admin/dispatch-rules` 返回 5 组 13 条（权重/自动派单/超时/积压/运行态）；`PUT` 批量保存返回"规则已保存并立即生效" |
| 规则页 | 5 个分组、13 行、11 个数字控件 + 2 个开关，运行态只读；保存成功提示 |
| 看板横幅 | 显示"运行正常 待派 0 单 · 在岗 0 人 · 最长等待 无积压"+ 当前两档阈值与暂停/恢复规则 |
